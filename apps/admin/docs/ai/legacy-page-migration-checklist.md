# 旧页迁移检查清单

适用范围：把 legacy admin 页面迁移到当前项目时，作为落地前和联调前的强制检查项。

## 1. 页面归类先行

- 先判断页面属于哪种 recipe：`list-query-standard`、`form-three-mode`、`profile`、`business override`。
- 能复用列表/表单模板的页面，不允许先写散装页面再回头收敛。
- 只有在详情页明显不是只读表单时，才允许做独立 detail page。

## 2. 列表筛选项检查

- 普通筛选项必须优先使用模板字段：`input`、`select`、`date`、`date-range`。
- 日期范围禁止再用 `custom + RangePicker` 实现。
- 可搜索下拉禁止再用 `custom + Select` 实现；优先走模板 `select` + `selectProps.showSearch/filterOption/onSearch`。
- 筛选项变更默认不自动触发查询；只在点击“查询”时请求，`重置` 例外。
- 桌面端检查日期范围、普通输入、下拉框是否能和同排筛选项稳定同行显示。

## 3. 表单与详情检查

- 新增/编辑表单必须保留必填标识，不要设置 `requiredMark={false}`，除非页面有明确视觉要求。
- 详情优先复用 `readonly` 表单模式，不要额外复制一套只读展示结构。
- 首屏必须覆盖三种状态：参数非法、详情加载失败、正常加载成功。
- `readonly` 模式下不允许出现可提交动作。
- 对每个保存/提交动作分别记录“校验范围”和“提交范围”；旧页局部校验后提交完整对象时，新页也必须局部校验后读取完整 form store，不能把 `validateFields(nameList)` 的返回子集直接作为 payload。
- 隐藏字段、未参与校验的可编辑字段、上传字段都必须进入字段对照；除非旧接口明确是局部 patch，否则不能因字段不参与校验而省略提交。

## 4. 路由与运行时检查

- 路由组件只从 `react-router-dom` 引入 `Navigate`、`useNavigate` 等对象。
- 禁止出现 `antd` 误导入路由组件的情况。
- 列表页至少点测一次：新增、编辑、查看三个入口都要能正常跳转。
- 表单页至少点测一次：保存、返回、错误态重试都要能正常执行。

## 5. 操作列宽度检查

- 操作列宽度必须按“同一时刻可见的按钮集合”计算，不能把被折叠进“更多”的按钮也按直出宽度计算。
- 2 字按钮按 `28px` 估算，4 字按钮按 `56px` 估算，再加分隔符和左右余量。
- 常见口径：
  - `单个 2 字按钮`：`28 + 16 = 44`
  - `查看 + 编辑 + 更多`：`28*3 + 13*2 + 16 = 126`
  - `编辑 + 删除`：`28*2 + 13 + 16 = 85`
  - `查看权限 + 编辑 + 更多`：`56 + 13 + 28 + 13 + 28 + 16 = 154`
- 注释里的计算过程必须和实际常量一致。

## 6. 列宽一致性检查

- 同类资源编号列宽度保持一致。
- 时间列优先使用统一宽度，避免同域页面一页一个值。
- 同域列表的主标识列宽度要统一，不允许无理由漂移。

## 7. 权限检查

- `readonly` 页面走读权限，`add/modify` 走写权限。
- 按钮权限需要同时核对“页面可进”和“行操作可见”两层。
- 至少验证一种“有页面权限但无按钮权限”的场景，避免操作列误显。
- 删除、编辑、营销设置、审核等核心动作必须单独核对“按钮是否出现”；按钮消失本身就是回归，不只检查点击链路。
- 核心动作不得把“是否展示”和“是否拿到执行主键”写成同一条判断；`visible 条件 / disabled 条件 / 执行主键 / fallback 主键` 必须分开冻结。
- 若旧页依赖 `questionId`、`modelId`、`orderId` 等业务主键，必须验证“通用 `id` 缺失但业务主键存在”时，动作仍然可见且可执行。
- 若旧页在 `uploadFlag`、局部嵌套记录或其他 legacy 可空字段缺失时仍展示动作，必须验证新页不会因这类字段缺失把动作误隐藏。

## 8. 接口与参数检查

- 接口路径和方法优先以 `docs/api/api.md` 为准；若暂时沿用 legacy 接口，必须在实现说明里写明。
- 依赖路由参数的页面必须先校验参数：例如 `id`、`resourceId`、`ownerId`。
- 列表页要明确空态、失败态、部分数据态的反馈文案。
- 每个非表单写动作都必须单独冻结请求合同：`endpoint / method / payload 来源 / 完整对象更新还是局部 patch / 状态值映射 / null 与 undefined 处理 / 成功判定`。
- 每个表单写动作都必须冻结 `校验字段集合 / 完整提交字段集合 / payload 组装位置`，并与旧页实际提交对象逐项对照。
- 默认值必须区分“首屏 UI 值 / 组件内部值 / 请求 payload 值”；三层不一致时，必须明确映射位置。
- 枚举展示必须对未知值兜底，避免新增枚举或脏值导致空白或崩溃。

## 9. 交付前最小验证

- 已按 `docs/testing-standards.md` 记录所选 `L0-L4`、选择依据、命令和结果
- 普通单页迁移默认按 `L2` 做 focused verification；涉及共享能力时，已用 import/reference 搜索与 workspace/package 依赖关系界定 consumers/suites 后按 `L3` 验证
- 仅在发布收口、依赖/构建链升级、明确要求、无法界定影响或项目批次/PR closeout 要求时升到 `L4`
- 至少补一条 happy path 测试
- 至少补一条失败/边界测试
- 手工点测一次关键跳转链路
- 至少补一条核心动作存在性测试，优先覆盖删除、审核、导出、营销设置等高风险按钮
- 涉及复杂组件时，至少补一次真实交互点测或自动化回归
- 表单保存测试按旧接口完整保存合同精确断言实际请求 payload 的完整字段集合，不能只抽查代表字段；存在局部表单校验时，必须覆盖页面实际存在且未参与校验的普通字段、隐藏字段和上传字段，并覆盖校验失败不提交
- 已按所选等级完成最终一次必要 typecheck/build；build 含类型检查时未重复 typecheck，较广检查覆盖较窄检查时未重复执行
- 涉及真实浏览器、登录、跨页面、权限或发布门禁时，Browser Mode/E2E 仍按测试标准执行，且 E2E 仍先构建候选
