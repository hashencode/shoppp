# 表单迁移期执行规则

## 1. 文档定位

### 1.1 文档目的
在“旧项目 -> 当前项目”迁移周期内，统一所有后台表单页迁移的执行标准。

核心目标只有一条：
- 用当前项目页面展示（UI/布局/组件规范）
- 沿用旧项目业务逻辑（接口、权限、参数、校验、交互语义）

本规则是迁移期作战手册，和长期骨架规范并行使用。

### 1.2 适用范围
- 业务域：所有管理后台表单页
- 表单类型：`add / modify / readonly`
- 当前项目基线：React + TypeScript + Ant Design + `template-kit`

### 1.3 与长期骨架规范的关系
- 本文用于迁移期“旧页逻辑 1:1 搬运”的执行规则。
- 若是新增基础三态表单页，或迁移页已经能稳定同构到标准骨架，优先阅读 `docs/ai/page-guardrail-recipes.md`。
- 满足基础表单条件的页面，优先接入 `BasicCrudFormRecipe`；复杂字段和特例流程仍按 `business override` 处理。

## 2. 迁移总原则（强约束）
1. UI 可升级，逻辑不降级。
2. 默认 1:1 功能迁移，不做交互优化，不做功能删减。
3. 旧页有的逻辑，新页必须具备；旧页没有的交互，新页默认不新增。
4. 若“新 UI 规范”与“旧逻辑”冲突，优先保证旧逻辑正确，再在新 UI 下表达。
5. 验收标准是“功能行为一致”，不是“代码结构一致”或“视觉像素一致”。

## 3. 标准执行流程（每个表单页都执行）
1. 对照阶段：先给出“旧页 -> 新页”功能迁移清单。
2. 设计阶段：确定“新展示 + 旧逻辑”边界，不做未确认优化。
3. 实现阶段：先迁逻辑，再贴合当前项目组件表达。
4. 联调阶段：同账号、同路径、同操作逐项对比旧新行为。
5. 验收阶段：清单全通过才算完成，缺一项都算未完成。

## 4. 旧逻辑迁移清单（必须逐项对照）

### 4.1 参数与模式
- `mode` 解析：`add / modify / readonly` 与旧页一致。
- `id`/资源标识校验与错误分支一致。
- 非法参数必须有明确错误反馈。

### 4.2 数据加载
- 首次加载时机与依赖条件一致（避免多余请求）。
- 请求成功后的回填逻辑一致（包括默认值、回显规则）。
- 请求失败态一致（提示、重试、返回路径）。

### 4.3 提交与重置
- 提交参数结构一致（字段名、类型、嵌套结构组装规则）。
- 校验范围与提交范围必须分别对照：旧页若用字段清单做局部校验，但提交完整 `formData`，新页必须先局部校验，再通过完整 form store 组装 payload；禁止直接提交 `validateFields(nameList)` 的返回子集。
- 隐藏字段、未参与校验的可编辑字段和上传字段必须纳入完整 payload 对照；只有旧接口明确为局部 patch 时才能主动裁剪字段。
- 提交成功/失败反馈一致。
- 重置行为必须覆盖“表单字段 + 复杂组件状态”。

### 4.4 权限与可见性
- 路由权限、按钮权限、数据权限语义分层一致。
- `readonly` 模式必须阻断提交（UI 禁用 + 行为硬阻断）。
- 不允许引入额外 role 硬编码判断覆盖旧逻辑。

### 4.5 复杂组件
- 复杂字段（如 `Cascader / TreeSelect / RemoteSearchSelect`）默认同构迁移。
- 若旧页为远程搜索/异步选项字段，新页必须保留“可检索、可加载、可回填”能力；禁止降级为仅初始静态 options。
- 默认展开/收起策略与旧页一致。
- 回填与提交时的节点处理逻辑一致。
- 搜索、回填、清空等交互链路一致。

## 5. 通用风险、教训与规避
1. 只迁了页面结构，漏迁了业务逻辑。
- 规避：每次迁移前先输出“旧页功能对照清单”，逐项验收。

2. 新页默认行为覆盖了旧页语义。
- 典型：默认值、提交组装规则、联动策略变化。
- 规避：所有默认值以旧页为准，模板默认行为仅在旧页无定义时启用。

3. 重置逻辑只清理了表单，未清理复杂组件状态。
- 规避：重置必须定义为“全状态重置”，明确列出要清空的每一类状态。

4. 开发环境双请求引发误判。
- 典型：`React.StrictMode` 下 effect 双执行（仅开发环境）。
- 规避：先区分开发行为与生产行为，再判断是否真有重复请求缺陷。

5. 表单操作区样式与系统基线不一致。
- 规避：可编辑模式（`add/modify`）统一使用底部固定工作条；`readonly` 不显示工作条。

6. 表单初始化副作用导致重复加载或渲染抖动。
- 规避：传入 hook/controller 的请求函数默认使用稳定引用（如 `useCallback`）。

## 6. 强制防错动作
1. 初始化加载稳定性检查。
- `fetch/update/save` 若依赖外部变量，必须 `useCallback` 包裹。
- 代码评审需显式确认“初始化 effect 依赖不抖动”。

2. 字段组件同构检查。
- 旧页是复杂组件时，新页默认同构迁移，不得先降级为 `Input / Select` 简化版。
- 对主流程必填字段，必须额外验证“输入关键字后可返回候选项”，再允许宣告迁移完成。
- 如确需替换，必须先给出“语义等价证明”（回填、提交、校验三项都一致）。

3. 成功判定口径检查。
- 迁移前明确旧页按“业务码 / data / message”哪一种判定成功。
- 新页必须沿用旧页口径，不得页面内各自猜测。

4. 反馈语义对齐。
- 轻量结果用 `message`。
- 高风险或旧页明确使用强反馈的写操作，沿用 `modal` 语义。

5. 隐藏字段检查。
- 若旧页存在 `id / targetId / parentId` 等隐藏主键字段，新页必须保留。

6. 局部校验与完整提交检查。
- 静态搜索旧页 `validateField(nameList)` 和新页 `validateFields(nameList)` / `validateFieldsWithScroll(form, nameList)`，逐个确认校验成功后的 payload 来源。
- 局部校验只决定是否允许提交，不得隐式决定提交字段集合；完整对象保存应在校验成功后读取完整表单值。
- 回归测试必须按旧接口完整保存合同严格断言实际请求 payload 的完整字段集合，优先使用 `toEqual` 或等价的精确白名单断言；不得只用 `toMatchObject` 抽查代表字段。存在局部校验时，该断言必须覆盖页面实际存在且未参与校验的普通字段、隐藏字段和上传字段，并覆盖校验失败不请求；页面不存在的字段类型不强制为测试造数据。

## 7. 验收清单
- [ ] 新页功能点与旧页逐项对齐，无缺失
- [ ] 请求时机、请求次数与旧页语义一致
- [ ] 提交参数结构与旧页一致
- [ ] 重置行为稳定且可重复
- [ ] `readonly` 模式完全阻断写操作
- [ ] 错误态/空态/加载态反馈完整
- [ ] 至少完成一组有权限账号与一组受限账号对比
- [ ] `add/modify` 模式的保存/重置位于底部固定工作条，`readonly` 无工作条
- [ ] 初始化加载无重复请求抖动（区分严格模式与真实缺陷）
- [ ] 所有写接口成功判定口径与旧页一致
- [ ] 所有必填字段具备“校验规则 + 可见必填标识”双重一致性
- [ ] 若存在局部校验，已按旧接口完整保存合同精确断言请求 payload 的完整字段集合，且校验失败不会发送请求

## 8. 红线
1. 未做对照清单就直接改代码。
2. 用“模板默认行为”替代旧页已定义业务逻辑。
3. 以“看起来差不多”作为验收标准。
