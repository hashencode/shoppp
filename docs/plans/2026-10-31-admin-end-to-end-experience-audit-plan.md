# 管理后台全流程用户体验审计计划

## 1. 目标与权威

以首次开店商家和日常运营人员的身份，实际操作 Shoppp 管理后台，评估排版布局、交互反馈和业务流程。交付按任务顺序组织的图文报告；每个关键操作节点有截图，每条修改建议有现场证据、用户影响、修改理由、具体方案和验收方式。

本文件是本次体验的固定执行入口，拥有本次审计的范围、单元状态、阻塞、下一动作与收尾。切换聊天、上下文压缩或更换执行者后，先读本文件及末尾 Execution Checkpoint，再读当前单元关联的证据继续；不得只依赖聊天记忆。

- 上游依据：本次用户请求、2026-10-31 的体验方案，以及随后要求保存计划、允许自行测试登录和支付的补充说明。
- 分类：独立、有界的知识工作计划，交付体验发现与改进建议。
- 继承基线：当前后台实际运行版本、现有业务能力、共享组件和后台规范。规划时仅检查了路由及说明文档，尚无本轮界面体验结论。
- 产品权威：`docs/plans/2026-08-13-001-refactor-shoppp-product-master-plan.md` 及其指向的产品计划继续拥有产品序列与交付权威；本计划不接管 REL、Candidate、DC 或 PG。
- 并行边界：现有表单、导航和装修编辑器等计划继续拥有各自实施与验收。本次重新取证，可关联其背景，但不复用旧图作为本次体验证据，不重开历史计划。
- 显式取代：本文件取代聊天中初版体验方案，作为本次执行依据；不取代任何产品或代码实施计划。
- 尾部归属：本计划负责截图、发现、覆盖说明、测试数据处置和报告收口。代码修复需后续独立计划，不自动转入实施、提交、部署或 PR。

用户已于 2026-10-31 要求开始，正式体验已执行；测试授权持续有效。

## 2. 已确定的操作授权与环境边界

用户已明确：这是测试环境，涉及登录、支付等测试可自行进行，无需逐项征得同意。此授权随本计划接续保留。

- 可自行完成测试账号登录、退出、无效凭证校验、适用的激活、密码找回与重设、重新认证和不同测试角色切换。
- 可自行创建和编辑测试数据，测试商品、库存、内容、导航、设置、主题草稿，以及测试环境内的业务发布与回滚等实际界面能力。
- 可自行前台下单、使用支付服务商测试模式完成支付，并测试适用的失败、取消、返回、订单取消、退款和履约分支。测试环境业务发布不等于代码部署或生产推广。
- 用户、角色、邀请和通知只作用于专用测试账号、受控测试收件箱或测试接收器。保留可继续进入后台的管理员账号，避免测试阻断后续体验。
- 执行前自行核对后台、API、数据库或环境身份及支付模式确属测试范围；核对是取证步骤，不是新增确认环节。测试入口指向生产、真实扣款或真实履约时，不将其视为本次授权范围。
- 测试凭证从现有配置、账号资料或受控测试渠道查找，不把密码、密钥、重设令牌或完整支付信息写入计划、报告或截图索引。
- 首选带真实测试后端的环境。模拟响应、手工造数或未完成支付服务商回调的订单必须标注，不能据此声称真实支付闭环已通过。
- 账号、支付配置、回调或测试数据确实缺失时，记录具体缺口，继续不依赖它的单元；只对无法自行解决的必要输入请求补充，不重复请求操作许可。

本次允许通过界面改变测试业务状态，不包含修改产品代码、清空共享测试库或为体验而重置其他人的数据。

## 3. 用户视角、体验范围与深度

### 两种主要视角

1. **首次开店商家**：理解首页和导航，跟随引导配置店铺，准备商品、内容和店铺外观，判断下一步及完成条件。
2. **日常运营人员**：查找与维护商品，处理订单和履约，查看数据，管理权限和异常任务。适用时使用受限测试角色，核对权限不足时的提示与恢复路径。

首次操作主要依靠界面提示和菜单，不提前用代码推导最佳路径。先记录找不到入口、术语不清或需要猜测的地方，再用只读代码、配置或日志查证；查证结果单独说明。

### 覆盖原则

- 按执行时实际可见菜单建立完整入口清单，并与路由核对，覆盖主要入口、详情、新建/编辑入口，以及适用的 Drawer、Modal、菜单和编辑器。
- 所有主要模块完成首轮检查；核心业务链完成实际操作；其他模块至少完成代表性的主要任务，不能仅打开首页就记为完整覆盖。
- 第二轮补查空列表、无搜索结果、字段错误、未保存离开、取消、返回、加载、提交反馈、权限不足和可恢复错误。正常操作中未自然出现的状态，仅在专用测试数据上作适度探查，不进行服务压测或全面故障注入。
- 相关流程优先复用同一批测试对象，形成“配置店铺—准备商品—前台购买—后台处理—报表核对”的关联链。不同订单状态分支使用独立测试订单，避免互相破坏前置条件。
- 前台用于商品与装修结果核对、下单及支付闭环；本计划不扩展为全站前台设计审计。
- 主链以当前可用的 `fashion-store` 运行入口为起点；开始时核对实际可用模板及版本。其他模板仅在当前后台确实提供且差异影响任务时记录适用性，不据此增删产品模板或冻结 Candidate Template Matrix，也不替代正式 DC3。
- 不承诺穷举全部数据、角色和状态组合。报告必须列清已操作、仅查看、受阻、未覆盖及不适用项。

### 跨页面检查维度

| 维度     | 观察内容                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------ |
| 排版布局 | 主次层级、内容密度、分组、留白、对齐、表格宽度、长表单、按钮位置、滚动后的可操作性、溢出和遮挡         |
| 交互反馈 | 可点击性、搜索筛选、排序分页、加载、保存、取消、重试、校验、成功提示、状态变化与恢复路径               |
| 业务流程 | 入口是否可发现、术语是否理解、下一步是否明确、是否重复填写或跳转、上下文是否保留、任务是否真正完成     |
| 可访问性 | 标签和名称、错误关联、键盘可达性、焦点可见性、关键弹层与返回后的焦点、非颜色状态表达、放大后的可操作性 |
| 一致性   | 同类任务的导航、表单、按钮、文案和反馈是否一致，差异是否有业务理由                                     |

桌面主视口默认 1440×900；补查 1280×800 和关键页面 200% 缩放。首轮保持同一语言与主题并记录；随后检查实际支持的语言切换及浅/深色主题在共享布局、复杂表格、表单、弹层和编辑器等代表页面的表现，不机械复制全部截图。无必要时不开展完整手机端后台审计。

可访问性检查针对实际组合后的体验；沿用现有组件的行为归属。任何自定义焦点或 ARIA 建议必须有可复现缺口，不能因假设收益建议增加全局播报或重复机制，也不凭截图声称符合完整 WCAG 标准。

## 5. 截图、节点与证据规则

### 每个节点如何记录

1. 观察当前页面，用最新界面状态定位控件，再执行操作。
2. 在进入页面、展开关键区域、完成关键输入、触发校验、提交前后、取消/返回、状态转换或恢复结果等判断节点取证，不为每次点击或按键单独截图。
3. 正常结果待画面稳定再截图；加载、错误或阻塞本身是发现时，单独保留并明确标为该状态，不冒充正常完成画面。
4. 保存后实际打开检查，确认页面、状态、视口、内容完整性及清晰度。空白、错页或意外裁切的图重新拍摄；长页面补拍关键区域。
5. 立即写节点记录与初步发现，再进入下一个节点；一个任务结束后同步检查点，不能只在聊天中留记录。

截图取自本次浏览器实际操作。默认采用应用内浏览器及其可用控制和截图能力；优先使用已经打开的目标页面，避免无理由刷新破坏现场。需要不同浏览器能力时按现有工具和用户偏好处理；不因测试授权推定用户授权直接使用 Playwright CLI/MCP。截图不能可靠保存或查看时，先解决取证能力，不继续积累无证据结论。

### 编号与索引

- 本轮 run ID：开始时按北京时间生成 `YYYYMMDD-HHmmss-admin-ux`，同一轮跨上下文继续使用；明显更换环境或版本时记录分段，必要时新建 run。
- 节点 ID：`N001` 起连续编号。截图 ID 为 `SS001` 起连续编号，文件名例如 `SS001-U2-login-initial.png`；补拍和前后对照各有独立 ID。
- 发现 ID：`UX-001` 起稳定编号；合并重复发现时保留原编号到主发现的映射。
- 节点索引字段：节点 ID、所属 U、用户角色与目标、北京时间、页面/路由、动作摘要、实际结果、体验状态、截图 ID/路径、相关发现 ID。
- 体验状态采用“顺畅 / 有摩擦 / 受阻 / 未验证”，与单元执行状态分开。
- 一张图可支持多个发现；一个交互发现可关联前后多张图。每个关键节点必须有有效截图或具体阻塞记录，每个正式发现必须关联截图及可复现步骤。
- 保留未经标注的原图；局部放大、箭头和方案示意作为派生图，明确区分当前界面与建议方案。展示副本如需遮盖敏感信息需标注，原始敏感内容不进入公开交付。
- 不复用旧截图、旧报告或缓存状态作为本轮事实；参考资料只能辅助解释背景。

## 6. 发现与建议的写法

每条发现至少包含：

| 字段             | 要求                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| 编号与位置       | 稳定 UX ID、U/节点 ID、页面与截图引用                                          |
| 用户目标与复现   | 用户希望完成什么，最短复现步骤及必要前置条件                                   |
| 实际现象         | 精确描述观察到的布局、交互或流程，不把猜测写成事实                             |
| 用户影响与理由   | 解释困惑、误操作、遗漏、重复劳动或任务受阻如何产生                             |
| 修改方案         | 说明哪些信息、分组、控件、文案、位置或步骤需要怎样调整，优先沿用现有组件和规范 |
| 验收方式         | 修改后按什么步骤观察什么结果；必要时列出不能退化的现有行为                     |
| 优先级与结论类型 | P1/P2/P3；已确认问题 / 待验证疑点 / 审美与偏好建议                             |

优先级定义：P1 为任务阻塞、明显误导关键业务决策或容易造成错误业务操作；P2 为任务可完成但有明显摩擦、信息不清或一致性问题；P3 为不妨碍完成的视觉与细节优化。确有更紧急的问题时单独说明实际影响，不机械套级。

交互结论同时提供步骤与前后截图；必要时附最小技术查证，注明何处来自界面、何处来自查证。重复模式归纳为共性问题并列出具体受影响页面。保留做得好的部分与建议维持的行为，不以发现数量为目标。

复杂结构调整可附简短布局示意或前后流程说明；未经验证的设计方案明确标为建议，不伪装为现有截图或已实现结果。

## 7. 文件组织与版本基线

唯一执行入口为本计划。正式开始时在 `docs/progress/admin-experience-audit/<run-id>/` 创建以下证据，不提前填充虚构结果：

| 文件                                         | 用途                                                                                                                  |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `report.html`                                | 可在浏览器阅读的图文报告，含问题卡片、节点展开、原图入口和覆盖限制                                                    |
| `report.md`                                  | 按任务顺序的图文报告、全部节点及体验状态、发现详情、优先级建议、保留项和限制说明                                      |
| `index.csv`                                  | 节点、截图、发现的对应关系及逐项覆盖事实；记录主要入口、任务分支为已操作、仅查看、受阻、未覆盖或不适用                |
| `coverage.csv`                               | 路由与任务分支的覆盖事实，具名列出未验证部分                                                                          |
| `findings.json` / `nodes.json`               | 正式发现与节点的结构化副本，编号及引用与报告一致                                                                      |
| `manifest.md`                                | 环境、运行版本/构建身份、账号角色、支付模式、视口/主题/语言、测试对象 ID 与操作回执、版本分段及数据处置记录，不存凭证 |
| `verification.md` / `screenshot-hashes.json` | 交付核验回执及原图校验和，不代替产品业务验收                                                                          |
