## 使用方式

有 `settings.read` 权限的管理员从后台根路径进入 `/welcome`。六个步骤可以自由进入；待处理检查项后面的文字箭头链接直接进入有权访问的编辑页面或固定分组。保存设置后返回指南会重新检查。缺少 `settings.read` 的用户仍可从指南的“可访问的编辑页面”进入其他有读取权限的编辑器，但看不到配置检查结论。旧 `/settings/launch` 地址继续提供商业设置。

“基础与联系方式”进入 `/settings/contact`。有 `settings.write` 权限的管理员在此维护客服邮箱、隐私联系邮箱、公开显示选择、电话、服务时间及其时区、可选的实体地址和社交媒体链接，填写变更原因后保存。两个邮箱仍以 `launch_configuration` 为唯一存储来源；其余字段保存在 `contact_profile`。只读账号可查看，不能保存。保存时同时检查邮箱配置版本和联系方式资料版本；若提示冲突，应先核对并重新加载最新值，再提交需要保留的修改。

实体地址和社交媒体链接均可为空，适用于纯线上商店。地址需要完整填写才能发布；地图仅使用管理员确认的 HTTPS 外部链接。社交媒体只显示已填写、有效且设为公开的链接，不会自动填入平台首页。已有邮箱值默认不公开，须由管理员明确选择公开。不要把访客留言表单当作可用的收件渠道：正式 Contact 页面目前提供已确认的邮箱、电话及外部链接，留言表单只用于模板对照。

自动检查与人工任务分别呈现。顶部显示“通过数/固定检查总数”以及待处理、无法检查、无权检查的数量；各检查项显示具体状态和原因。步骤标题右侧以图标提示汇总状态，并提供文字提示和可读名称。无法检查和无权检查不会从分母删除。六个步骤始终展示并可分别展开，不保存任何“已上线”或人工验收状态。13 项统计只覆盖原有上线配置检查；身份、政策正文、内容、导航、集合及主题集中列在“其他开店事项”，由对应编辑器核对草稿、发布、候选和线上状态，不把入口本身算作配置完成。支付凭证、Turnstile 与备份绑定等环境问题明确指向部署维护者，不显示无法解决问题的后台快捷链接。

## 检查口径

| 领域         | 服务端依据                                                       | 范围限制                                         |
| ------------ | ---------------------------------------------------------------- | ------------------------------------------------ |
| 基础配置     | 已保存的商业配置记录及有效的客服、隐私邮箱                       | 环境默认值不表示管理员已经确认                   |
| 公开联系方式 | 已保存的联系方式资料，且至少一个公开邮箱、电话或实体地址联系电话 | 地址和社交链接可为空；有效邮箱本身不代表已经公开 |
| 商品         | 默认币种下已发布商品、active SKU、有效价格及可用库存             | 至少一个可售 SKU，不保证所有商品或所有币种       |
| 配送         | 有效区域、国家、方式及所选方式与各国家的区域关联                 | 不证明所有重量和币种均可报价                     |
| 支付         | 服务端凭证格式与环境支付模式要求                                 | 不连接支付商，不证明收款或回调成功               |
| 政策         | 既有政策确认、链接格式及生产占位域名检查                         | 正文准确性需要人工确认                           |
| 复核         | 超卖、预留时长、Turnstile 与备份配置                             | 配置存在不代表实际作业已经成功运行               |

管理员仍需在现有主题流程检查店面、品牌与政策正文，并人工核验完整购物流程。指南不会创建支付或触发生产发布。自动全绿不替代 REL/DC/PG 的正式发布证据。

保存联系方式只更新后台资料；已建立的 Experience 预览和已批准快照保留当时的公开联系方式及版本。新预览或新批准快照才会读取新资料。上线前在新预览中检查 Contact、Header、Footer 的邮箱、电话、地址、地图链接和社交链接，核对没有示例商家信息；同时记录该快照的联系方式版本。指南通过状态不等于该版本已发布。

## 结果与恢复

- `passed`：当前配置上下文中的检查通过。
- `needs_action`：检查确认了需要处理的问题，按步骤入口修正。
- `unavailable`：配置或领域查询失败；重新检查，持续失败时由维护者排查对应 API/数据库。
- `restricted`：当前账户缺少领域读取权限；由具备相应权限的人检查。

API 摘要携带检查时间、环境、配置保存时间及默认币种，响应禁止共享缓存；指南顶部展示通过数/固定总数和各非通过状态的数量，不展示这些上下文字段。每次检查使用同一份配置；重新检查期间旧的通过数不作为当前结果，概要卡片与步骤列表保持原有高度，直至新响应结束。领域失败不会抹掉独立领域的结果；配置读取失败时不会拼接默认值或历史结果。

步骤内检查项以无序列表展示。包含未通过检查的步骤在结果返回后自动展开，全部检查通过的步骤默认折叠；手动展开或折叠只影响当前页面状态。

支付与 Turnstile 密钥、备份凭证和绑定由部署维护者按现有环境配置流程处理。摘要仅返回问题代码，不返回密钥。商业设置页面不能通过修改客户端的凭证标志来改变服务端事实。运行健康单独加载，其成功或失败不计入准备进度。

## 扩展检查

1. 在 `packages/contracts/src/platform.ts` 的固定集合中定义稳定 ID 与所属步骤，明确通过口径和最小读取权限。
2. 在 `apps/api/src/settings/setup-guide.ts` 使用同一次配置输入，复用权威业务判断；查询失败返回无法检查，权限不足时不执行领域查询。
3. 在 Admin 指南中补充中英文检查名称、原因文案及处理入口。未知原因必须保留通用待处理提示。
4. 补充对应 Workers 边界测试、contract 完整性测试和必要的页面测试。变更默认入口或返回旅程时补充浏览器证据。

不要保存推导的通过率、复制商业配置、推断生产主题，或把检查规则加入结账/发布门禁。改变这些边界需要单独的产品范围与计划。

## 部署后的验证

后续按既有发布流程部署时，由部署维护者在首个验证窗口内使用对应环境账号打开指南，确认检查时间、环境和默认币种，并实际保存一项允许修改的配置后返回重查。对只读账号确认无保存操作；对没有设置权限的账号确认原业务首页仍可进入。

查看 `/admin/settings/setup-guide` 的请求错误及耗时，关联响应的 `requestId`；关注大量 `unavailable`、反复 401/403 或与当前配置不一致的结果。预期结果是完整的固定检查集合、无凭证内容和正确的缓存头。遇到持续异常时先排查配置读取/领域数据源及会话权限；若确认为本次变更回归，按现有部署回退流程恢复上一版本。不要为恢复指南而扩大权限或绕过正式发布门禁。
